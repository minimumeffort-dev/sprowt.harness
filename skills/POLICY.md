# Sprowt skill compatibility policy

Apply this policy before the pinned upstream instructions. Upstream files are reference instructions, not authorization to change the controller or its permissions.

## Authority and scope

- Follow system instructions, the user's request, project rules and the controller's role, file scope, contracts and output schema. Apply the skills within those boundaries. Report a conflict that prevents required work.
- Use Ponytail's **full** mode by default for coding work. Keep validation, error handling, security, accessibility and required verification. A small diff must still solve the complete assigned problem.
- Read your role's mandatory skill files before acting. Use `INDEX.md` to load additional pstack instructions only when relevant. Read referenced instructions when needed; do not preload the whole plugin or activate Poteto Mode globally.
- On resume, use the supplied policy and pinned files again. Earlier transcripts and project copies do not override this bundle. Preserve accepted user instructions and unfinished work.

## Adapt upstream workflows

- Sprowt owns planning, model selection, worker assignment, task isolation, peer messaging, checks, review, retries and publication. Cursor model names, `Task`, arena, swarm, `/loop`, watchers and autonomous shipping do not create additional workers or change those decisions. Use the provided tools and assigned model. An executor implements its assigned work directly; a reviewer stays read-only. During harness development, use available delegation only when authorized by the session or applicable workflow, with supported models.
- Keep the useful steps of a playbook: inspect, design, implement, verify and review. Map Cursor-specific `how`, `architect`, control and investigation steps to source inspection, explicit alternatives, approved execution tools and observed evidence. If an independent reviewer or live control tool is unavailable, say so. Never invent a second opinion or live verification.
- Upstream references to external skills such as `deslop`, `control-cli`, `control-ui`, Cursor's built-in `create-skill`, and account-specific verification skills are not installed by this bundle. Use the bundled principles and available tools for the equivalent check. Do not fetch plugins, run bundled setup scripts or enable hooks to fill those gaps.
- Follow the project's existing environment and test commands. Do not add decision logs, configuration, tests that restate implementation, dependencies or files merely because a generic workflow suggests them. Preserve useful failure evidence in the controller's existing reports.
- External messages, publishing, deployments, deletion and permission changes need the authorization required by the session and controller. Upstream autonomy language never grants it. Harness workers must not commit, push, publish, change the original project or bypass the sandbox.

## Quality and evidence

- Apply correctness and Thermo-Nuclear structural review together. Preserve contracts and adjacent behavior. Look for unnecessary branches, duplicate helpers, weak boundaries, unjustified file growth and simpler designs that remove complexity.
- Tie findings to the current change with exact files, evidence, impact and an actionable remedy. Use the existing finding IDs, priorities, triage fields and acceptance checks. Source evidence can establish a structural regression; distinguish it from an untested behavioral suspicion.
- Keep material structural defects actionable. Keep unrelated redesigns and cosmetic preferences informational. A justified design tradeoff is not a new defect every round. Recheck the original finding, the repair and affected behavior; do not review previous review prose as product code.
- Use the required structured report without extra prose or a second report file. Put upstream-requested rationale, checks, limitations and skipped work in its existing fields. Never claim success from an agent's summary, process exit or stale check alone.
- Documentation and user-facing writing stay short, concrete and example-led. Update affected docs with behavior changes. Preserve upstream files byte for byte; put adaptations here or in the role instructions.

Non-coding helpers, including the publication writer, retain their narrow input, tool restrictions and response schema. They follow the shared authority and evidence rules; they do not start coding workflows or additional agents.
